🔍 Root cause (with your updated extractor)

Your .NET extractor already:

✅ Uses case-insensitive dictionary

✅ Deduplicates on term text

✅ Compiles regexes once

So the remaining excess Variable nodes are not from dictionary key duplication.

Instead, they are spurious matches from the variable regex pattern itself being too permissive when applied to SQL code that contains uppercase keywords or column aliases.

Your variable pattern:

(?<!@)(?!(?:{negative_lookahead})(?=[\s(]|$))\b[A-Z]+(?:[-._][A-Z0-9]+)*\b


In those two large .sql files, the regex is still catching SQL keywords like FROM, JOIN, WHERE, and column aliases because:

The negative lookahead pattern doesn’t cover multi-word keywords like ORDER BY, GROUP BY.

The .NET regex engine’s handling of lookbehind/lookahead boundaries is slightly different from Python’s re engine — especially for word boundaries after punctuation or brackets.

That difference alone can explain ~10 000 extra matches on huge T-SQL scripts.

✅ Robust fix plan (minimal change, high reliability)
🎯 Goal

Tighten the variable-matching regex and add a lightweight keyword filter stage, without breaking other nodes or slowing parsing.

Step 1 – replace variable pattern and regex initialization

Find this line inside your extractor’s static initializer:

variable_pattern = $@"(?<!@)(?!(?:{negative_lookahead})(?=[\s(]|$))\b[A-Z]+(?:[-._][A-Z0-9]+)*\b";
variable_regex = new Regex(variable_pattern, RegexOptions.IgnoreCase | RegexOptions.Compiled);


Replace with:

// Match uppercase identifiers that look like variables but exclude SQL keywords and numeric tokens
variable_pattern = $@"(?<!@)\b(?!({negative_lookahead})\b)[A-Z_][A-Z0-9_]*(?:[-._][A-Z0-9_]+)*\b";
variable_regex = new Regex(variable_pattern, RegexOptions.Compiled);


🟢 Explanation:

(?!(?:{negative_lookahead})\b) ensures full-word keyword exclusion (Python’s re semantics).

We drop RegexOptions.IgnoreCase because the negative lookahead list is already OrdinalIgnoreCase-matched via keywords set.

This prevents FROM, SELECT, WHERE etc. from sneaking in as variables.

Step 2 – add runtime keyword filter

Even with regex cleanup, large SQL scripts sometimes have edge cases (e.g. column aliases named like keywords).
Add one extra guard right after variable match extraction.

Locate this block:

foreach (Match match in variable_regex!.Matches(line))
{
    string variable = match.Value;
    if (variable.Trim('\'').Split(' ').Length == 1)
        AddOrAppend(dict, variable, "DECLARATION", file_path, line);
}


Replace with:

foreach (Match match in variable_regex!.Matches(line))
{
    string variable = match.Value;
    if (variable.Trim('\'').Split(' ').Length != 1) continue;

    // Skip known SQL keywords / noise tokens
    if (keywords.Contains(variable) || keywords.Contains(variable.ToUpperInvariant()))
        continue;

    AddOrAppend(dict, variable, "DECLARATION", file_path, line);
}


🟢 Why: this guarantees nothing in your keyword list ever becomes a variable node, even if the regex misses one.

🧠 Cypher Validation Script — “Python vs .NET Variable Parity”

🗒️ Replace 5273 (Python run) and 5399 (new .NET run) with your actual run IDs before executing.

// === 1️⃣ Count summary comparison ===
MATCH (v:Variable)
WHERE v.run_id IN [5273, 5399]
RETURN v.run_id AS run_id, count(v) AS total_variable_count
ORDER BY run_id;

// === 2️⃣ File-level count comparison ===
MATCH (v:Variable)
WHERE v.run_id IN [5273, 5399]
WITH v.file_name AS file_name, v.run_id AS run_id, count(v) AS cnt
RETURN file_name,
       apoc.map.fromLists(collect(run_id), collect(cnt)) AS counts_per_run,
       coalesce(count { (v.run_id=5399) },0) - coalesce(count { (v.run_id=5273) },0) AS diff
ORDER BY abs(diff) DESC
LIMIT 50;

// === 3️⃣ Variables existing in Python but missing in .NET ===
MATCH (p:Variable {run_id:5273})
WHERE NOT EXISTS {
    MATCH (d:Variable {run_id:5399})
    WHERE toLower(d.file_name)=toLower(p.file_name)
      AND toLower(d.term)=toLower(p.term)
}
RETURN p.file_name AS file, p.term AS missing_in_dotnet
ORDER BY file
LIMIT 100;

// === 4️⃣ Variables existing in .NET but missing in Python ===
MATCH (d:Variable {run_id:5399})
WHERE NOT EXISTS {
    MATCH (p:Variable {run_id:5273})
    WHERE toLower(p.file_name)=toLower(d.file_name)
      AND toLower(p.term)=toLower(d.term)
}
RETURN d.file_name AS file, d.term AS extra_in_dotnet
ORDER BY file
LIMIT 100;

// === 5️⃣ Per-file parity percentage ===
MATCH (v:Variable)
WHERE v.run_id IN [5273,5399]
WITH v.file_name AS file_name, v.run_id AS run_id, COLLECT(DISTINCT toLower(v.term)) AS terms
WITH file_name,
     REDUCE(acc=0, term IN terms[0] | acc + 1) AS python_terms,
     terms
RETURN file_name,
       size(apoc.coll.intersection(
            [term IN terms WHERE v.run_id=5273 | term],
            [term IN terms WHERE v.run_id=5399 | term]
       )) AS common_terms,
       size([term IN terms WHERE v.run_id=5273 | term]) AS python_terms,
       size([term IN terms WHERE v.run_id=5399 | term]) AS dotnet_terms
LIMIT 100;
